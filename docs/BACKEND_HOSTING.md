## Runtime and privacy boundaries

The existing Dockerfile installs the pinned `en_core_web_md` 3.7.1 model, loads it during the build, and starts the API as non-root UID 10001. It listens on port 8000; the Blueprint explicitly overrides Render's default `PORT` to match the command and container health check. This is supported by [Render's port binding rules](https://render.com/docs/web-services#port-binding). The Docker runtime uses the existing image command; no duplicate package installation or replacement start command is proposed.

Only signed guest workspace JSON belongs on the mounted disk. Read-only taxonomies stay in `/app/data`. `WORKSPACE_SECRET` is generated by Render instead of committed. Retain this secret securely for recovery: changing it invalidates existing guest cookies and breaks access to those guest workspaces. Do not print it in logs or include it in public evidence. The Docker build context allowlist includes application code, dependencies, and two taxonomy files; it excludes personal documents, environment files, Git history, and frontend artifacts.

Cookies are Secure, HttpOnly (set by the application), and SameSite=Lax. CORS permits only `https://resume.docheng.co.za`; localhost, wildcards, and the private Sites preview are absent. Uploads are limited to 10 MB. CORS is a browser control, not API authentication: the API remains a public endpoint with signed guest isolation and rate limits. No paid AI environment variables are supplied.

The Hostinger plan currently serves a static frontend. Creating this backend alone does **not** establish the application's required same-origin `/api` route. Do not point the static Sites edition at this API or change cookies to cross-site mode as a shortcut. A separately reviewed same-origin proxy/frontend hosting configuration and end-to-end cookie verification are required before primary-site cutover. No current placeholder backend is assumed to work.

## Acceptance and backup gates before real traffic

The repository's container CI at application revision `ce44344` passed the model, non-root runtime, guest isolation, document export, and restart durability checks reported for this release. It uses a 2 GB memory limit; it is not a throughput benchmark for the proposed 1 CPU service. No Docker build was run locally for this hosting proposal because Docker is unavailable on this machine.

After activation, inspect the actual deployed commit and build logs; confirm model initialization and a healthy `/api/health` response. Health alone does not prove durable storage. Verify UID 10001 can write the mounted directory: create two separate guest workspaces, save distinct documents, restart the service, and confirm both documents persist and remain isolated. Render's disk ownership behavior on the new mount still needs this live check; stop before production use if the mount is not writable. Never solve it by making guest data publicly readable.

Verify PDF/DOCX downloads, upload rejection limits, deletion/export privacy behavior, and the production frontend's secure cookie through its final same-origin route. Confirm API responses are not cached by the proxy. Keep the static Sites edition independent until its supported operations are intentionally changed and tested.

Render provides daily disk snapshots retained for at least seven days, but a snapshot is not an independent backup and restoring it overwrites the disk. Before real user data is accepted, define the backup owner, encrypted off-platform destination, retention, access controls, and restore test. Back up both workspace data and the corresponding signing secret securely, without placing either in Git or static hosting artifacts. A new empty disk is not a migration of any existing backend data. Existing-host backup discovery and any migration/cutover require separate verified evidence. See [Render disk snapshots and restore precautions](https://render.com/docs/disks).

For the existing Hostinger site's backup download, inventory, and local verification procedure, follow the [backup runbook](BACKUP_RUNBOOK.md). No actual server backup has been created or verified for this release yet. The local verifier does not itself create a provider backup or restore a server.
